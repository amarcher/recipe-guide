Design decision

The kid/adult slot split

How do we model a dinner where adults and kids eat different things?

One decision, three options, a recommendation at the end. Most of the time it won't matter — most dinners, everyone eats the same thing. But when it does matter, the schema choice affects grocery rollups, sync, and the cook-night UI.

The situation

Friday dinner: two meals in one slot

The menu skeleton landed on this for Friday:

Slot: Fri-DINNER Eaters: ADULTS + KIDS — Adults — shakshuka (honors the "been curious" aspiration) — Kids — quesadillas (kidRules.reliableHits)

Same slot, same evening, same kitchen — but two separate CookCards. Shared ingredients (eggs, bell pepper, cheese on both) can be aggregated into one grocery list. But when you walk up to Friday night and hit "Cook," what does the app actually open?

That's the question. The schema has to pick a shape.

Option A

One row, two chosen candidates

PlannedMeal { day: Fri, slot: DINNER, eaters: [ADULTS, KIDS], adultCandidateId: "shakshuka", kidCandidateId: "quesadillas" }

One row per slot. Two nullable FK columns — when both groups eat the same thing, only one is set (or both point to the same candidate).

Pros

  • UI is naturally one card per slot — "Friday: shakshuka / kids get quesadillas"
  • Calendar view stays clean, one meal per evening
  • The "everyone eats the same thing" case is trivially one row

Cons

  • Execution UI is forced to render two CookCards inside one screen (tabs, split view, or switcher) — new surface area
  • Mise and timers need a "which meal?" scope everywhere they're referenced
  • Asymmetric nullability — both-null is invalid, adult-null rare but possible; invariants leak into app code

Option B

Two rows, one slot

PlannedMeal { day: Fri, slot: DINNER, eaters: [ADULTS], chosenId: "shakshuka" } PlannedMeal { day: Fri, slot: DINNER, eaters: [KIDS], chosenId: "quesadillas" }

Two separate rows when groups diverge. Unique constraint on slot becomes (planId, day, slot, eaters), not (planId, day, slot).

Pros

  • Each meal is a first-class PlannedMeal — existing execution flow (mise, timeline, timers) drops in with zero changes
  • Grocery rollup, sync, and Meezing all just iterate PlannedMeals without special-casing
  • Kid quesadilla and adult shakshuka can cook at different times with independent timers, because they are independent

Cons

  • Calendar view has to render two cards for the same slot when split — mild visual overhead
  • "Everyone eats the same thing" is still one row, but now the `eaters` field has to enumerate ADULTS+KIDS — one extra bit of logic
  • You have to decide up-front whether to split (at skeleton time) or lazily (when the user picks different candidates)

Option C

Hybrid — one row plus optional kid variant

PlannedMeal { day: Fri, slot: DINNER, eaters: [ADULTS, KIDS], chosenId: "shakshuka", // the main meal kidVariantId?: "quesadillas" // null most nights }

One row per slot. The main meal is symmetric ("everyone's eating this"); a kid variant is an optional override. Asymmetric on purpose — adults are the cooks, so the adult meal is the spine.

Pros

  • Common case stays a single, simple row. Variant is null most of the time.
  • UI naturally renders the adult meal as the primary card with a subtle "kids are having X" strip
  • Matches how the household actually works — adult cooking the main, quickly assembling a kid alternative

Cons

  • Implicitly privileges the adult meal. If a night is truly "two equal meals" (e.g., a dinner party where adults do A and kids do B), it feels off
  • Every downstream query that aggregates meals (grocery, sync) has to remember to union chosenId + kidVariantId
  • Can't extend to a third group cleanly — what if a kid has an allergy and needs their own variant? You'd have to evolve to Option B anyway

What actually differs

Side-by-side on the concerns that matter

ConcernA · one row, two FKsB · two rowsC · one row + variant
Same-meal night (95% case) One row, one FK set One row, eaters = both One row, variant null
Grocery rollup code Union two FKs per row Iterate rows, done Union FK + variant per row
Sync / Meezing Needs "which meal" scope Drops in unchanged Needs scope on variant nights
Cook-night UI Tabbed / split screen Two cards side by side Primary + kid strip
Future third variant (allergy, guest) Hard — needs more columns Trivial — another row Hard — have to refactor to B
Calendar cleanliness Always one card per slot Two cards on split nights Always one card per slot

Recommendation

Go with Option B — two rows

Why: the split nights are real, and every other piece of the system we've been designing — grocery rollup, sync, Meezing, the existing execution flow — is already shaped around "one PlannedMeal = one thing you cook." Option B keeps that invariant intact. Options A and C both introduce special-case branches in every aggregation, and Option C boxes us in if a third variant ever shows up (kid allergy, dinner guest).

The cost we're accepting: when adults and kids eat differently, the calendar renders two cards for that slot. That's fine — honestly, it's accurate. On a split night, you are cooking two meals, and pretending otherwise hides work from the grocery list and sync layer.

What makes this safe to pick now: it's the shape that requires the fewest code changes in the existing CookCardView / mise / timer stack — which is the thing you most want to leave intact.

If you go with the recommendation

What unblocks, what stays open

Unblocks

  • The PlannedMeal schema finalizes: (planId, day, slot, eaters) unique, one chosenCandidateId FK.
  • The menu-skeleton prompt can commit to emitting a second slot entry for kid-variant meals instead of a side field.
  • Grocery aggregation, sync, and Meezing can all iterate PlannedMeal without branching.

Still open (for later, not now)

  • The candidate-generation prompt for per-slot calls — the next thing to design.
  • How the UI visually groups two same-day same-slot rows on the calendar (a subtle pairing affordance, not a merged card).
  • Whether "everyone eats the same thing but kids get a smaller portion" is a variant or just a scaling note on one row. Probably the latter — doesn't need schema help.
